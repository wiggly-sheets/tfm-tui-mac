# tfm audit — 2026-10-16

Read-only review of the working tree at `6926070` (`docs: add sync browsing and
sort keys to website table`). Nothing in this report was changed; the only file
added is this one.

## What this repo does

tfm is a terminal file manager built on Bun + OpenTUI. It browses, copies,
moves, deletes, trashes, extracts and compresses files; previews images and
video; opens a PTY shell; talks to network mounts; loads user plugins; and
handles kitty drag-and-drop. Roughly 80k lines of TypeScript (about 41k
excluding tests), macOS + Linux only.

Assumed load (from the code's own design, not a benchmark): a single interactive
user on a laptop or desktop, one process, one active operation at a time
(mutations are serialized through one shared queue). Directories are typically
tens to a few thousand entries. The threat model that matters here is the one
the code already defends against: untrusted archives, filenames with spaces or
leading dashes, and files the user cannot read without `sudo`.

## Must fix

### 1. High — Archive fallback can still create files/symlinks outside the staging directory through a symlink chain

**Plain English.** When you extract an archive, tfm first unpacks it into a
hidden temp folder next to the target, then checks nothing escaped and moves the
results into place. The JavaScript fallback unpacker writes symlinks in a second
pass "so a link written earlier can't be walked through by a later entry" — but
the same pass can chain a link into a link: the first symlink entry creates
`d -> /Users/you/.ssh`, and a later entry named `d/authorized_keys` is then
written *through* that link, landing in your home directory instead of the temp
folder. The containment check only looks at the entry's own name, and the
post-extraction cleanup runs after the damage and only watches the destination
folder and its parent, so the out-of-tree write is never seen.

**Evidence.** `src/fs/archive.ts:859-871`

```ts
const dest = path.resolve(base, e.name);
if (dest !== base && !dest.startsWith(`${base}${path.sep}`)) { skipped++; continue; }
...
mkdirSync(path.dirname(dest), { recursive: true });
try { symlinkSync(Buffer.from(data).toString("utf8"), dest); } catch { skipped++; }
```

`path.resolve(base, "d/authorized_keys")` is lexically inside `base`, so the
check passes; `mkdirSync(path.dirname(dest))` resolves the already-created `d`
link. The sweep that would notice is name-diff only:
`src/fs/fileops.ts:1339-1341` (destination + parent snapshots) and
`src/fs/fileops.ts:1367` (`sanitizeStagedLinks`, which by design runs after the
tool and can only remove the escaping link, not the file it already made).
The tar fallback has the same exposure through the upstream extractor:
`src/fs/archive.ts:681` `await new Bun.Archive(data).extract(destDir)`.

**Impact.** A crafted `.zip` (or `.tar` with `link/link` members) extracted on a
host without `unzip`/`tar` in PATH plants symlinks or directory trees in
attacker-chosen locations outside the extraction folder — for example a
`~/.ssh/authorized_keys` symlink, or a file in an autostart directory. It needs
the user to extract an untrusted archive and the fallback lane to be active
(`unzip` missing), which is why it is not Critical, but it defeats a
containment guarantee the code explicitly claims.

**Fix.** In the second pass, `lstatSync` each parent in the entry's path and
skip the entry unless every parent is a real directory inside `base` (reject
link-in-link outright). Apply the same guard to the tar fallback by extracting
to a fresh temp that contains no pre-existing links, or by rejecting archives
that contain symlink entries under the fallback lane. Add a regression test with
a zip holding `d` (symlink) + `d/x` (symlink).

### 2. Medium — A `../` archive member can silently overwrite an existing file in the destination folder, and the sweep cannot see it

**Plain English.** The spawn lane (`tar`/`unzip`/`7z`) writes a `../evil`
member relative to the staging dir, so it lands in the destination folder. tfm
catches this by comparing the folder's file list before and after the run. But
if `evil` already existed there, the name is in the "before" snapshot, the sweep
skips it, no escape is counted, and the archive is accepted — even though the
tool just overwrote the user's file.

**Evidence.** `src/fs/fileops.ts:1340-1341`

```ts
for (const name of afterDest) {
  if (name === stageBase || beforeDest.has(name)) continue;
```

The comment above (`src/fs/fileops.ts:1194-1198`) states the intent: anything
new outside staging is an escape artifact. A pre-existing name is actively
excluded, so an overwrite is invisible and `escaped` stays `0`
(`src/fs/fileops.ts:1362`).

**Impact.** Data loss. A malicious archive containing a member named
`../<predictable name>` silently replaces a file in the folder you extracted
into (e.g. a document with a name the attacker guessed), with no error and no
trash copy of the original.

**Fix.** Snapshot mtime+size (or inode) per name, not just the name set, and
treat any pre-existing entry whose stat changed during the run as an escape:
refuse the archive and report it. Cheaper alternative: run the tool in a
throwaway directory and detect traversal by comparing the file list the tool
actually produced.

## Should fix

### 3. Medium — "Empty Trash" confirmation runs a blocking `mount` on the UI thread (darwin)

**Plain English.** Choosing "Empty Trash" first counts the items so the prompt
can say how many. On macOS that count shells out to `mount` synchronously. On a
machine with a hung or stale network volume, `mount` can take up to the 10-second
timeout, and the whole TUI is frozen for that entire time before the dialog even
appears.

**Evidence.** `src/fs/fsutil.ts:214`

```ts
text = execSync("mount", { timeout: 10_000 }).toString();
```

Reached synchronously from `countTrashItems` (`src/fs/fsutil.ts:171-181`), which
is called directly on the prompt path in `src/fs/trashops.ts:470`
(`const n = countTrashItems(undefined, platform);`).

**Impact.** Up to a 10-second UI freeze on the confirm-then-act path, worse on
slow FUSE/NFS mounts. Every keypress and every repaint stalls with it.

**Fix.** The same table is already obtained asynchronously elsewhere
(`promisify(execFile)("mount", …)` in `src/fs/netmount.ts:51`). Make the
confirmation show immediately with a generic label and fill in the count when it
arrives, or cache the mount table (it changes rarely). At minimum, use
`execFile` + promise so the event loop stays free.

### 4. Medium — Every grid render re-serializes the whole listing up to four times

**Plain English.** To decide whether the screen changed, the grid build computes
four signatures — the render context, membership+size+mtime, membership only,
and content-only. It rebuilds the context array in each one, and three of them
`JSON.stringify` a string built from *every* listed entry. On a large directory,
or a recursive search that can return up to 200 rows, that is several full passes
over the entry list per frame, every watcher tick and every hover.

**Evidence.** `src/ui/ui-grid.ts:417`, `src/ui/ui-grid.ts:418-422`,
`src/ui/ui-grid.ts:445-449`, `src/ui/ui-grid.ts:452-463` — `baseSigParts()`
(`src/ui/ui-grid.ts:383`) is called once for `ctxKey` and again inside each of
`sigOf`, `structOf` and `contentSigOf`, and each of the last three maps the full
list into a joined string before `JSON.stringify`.

**Impact.** Avoidable CPU per frame; most visible as core pegged during rapid
navigation in large folders, or during a recursive search that is re-signed on
each keystroke/tick.

**Fix.** Compute `baseSigParts()` once per render into a local const, and build
the per-entry `name\0size\0mtime` key array once (`const keys = entries.map(...)`)
and reuse it for all three signatures instead of rebuilding it in each.

## Nice to have

### 5. Low — `require("node:fs")` inside an ESM module

**Plain English.** `open-url.ts` calls `require("node:fs")` inline. This only
works because Bun exposes `require` in ES modules; run the same file under Node
or a bundler that does not, and it throws `require is not defined` right before
the existence check that the code needs.

**Evidence.** `src/fs/open-url.ts:41`

```ts
const { statSync } = require("node:fs");
```

Reached on the Linux default-open path and on every reveal.

**Impact.** Runtime throw (caught by the surrounding `try`/`catch` here, so a
vanishing "no such file" error message rather than a crash) under non-Bun
runtimes. Portability only.

**Fix.** Import `statSync` from `node:fs` at the top, as the rest of the
codebase does.

### 6. Low — Tree copy and delete recurse one JS frame per child

**Plain English.** `copyTreeProgress` and `rmTreeProgress` call themselves for
each child entry. That is fine for normal trees but is not stack-safe for
pathologically deep ones, unlike `scanTree` and `walkTree`, which use an
explicit stack.

**Evidence.** `src/fs/transfer.ts:301` (`await copyTreeProgress(path.join(src, k), …)`)
and `src/fs/transfer.ts:347` (`await rmTreeProgress(path.join(root, k), sink)`).

**Impact.** Theoretical: path length limits allow only a few thousand nesting
levels, which is below the default stack budget. No realistic report of failure.
Listed for consistency with the iterative walkers elsewhere.

**Fix.** Only if it ever matters, port the same explicit-stack pattern used in
`scanTree`.

Findings left out to keep this readable: several obvious non-issues that are
already handled (see below), plus the plugin privilege model, which is
documented and intentional.

## What is already good

- **No shell anywhere.** Every external tool (`tar`, `unzip`, `7z`, `git`,
  `sudo`, `open`, `xdg-open`, `gio`, `mount`, `xattr`, `osascript`, `fd`) is
  spawned with an array argv, never a shell string. `search.ts:38-40` and the
  installer both pass an explicit `--` before the user's value.
- **Archive containment is deliberate, not accidental.** Staging directory,
  before/after snapshot sweep, symlink sanitizing pass, and mode masked to
  `0o777` so archives cannot restore setuid/setgid/sticky
  (`archive.ts:828-833`). The two findings above are the remaining gaps in a
  control that is otherwise well built.
- **Durable writes.** Files stream to an exclusive sibling `.tfm-part-*` temp,
  fsync, then hardlink-claim the destination; directories stage and rename. A
  crash cannot leave a half-visible file (`transfer.ts:104-150`, `:295-325`).
- **Serialized mutations.** One `sharedOpQueue` (`lib/op-queue.ts`) covers
  transfer, trash, extract and undo, so no two destructive ops interleave on the
  same paths.
- **Bounded memory.** Explicit caps on `JS_ARCHIVE_MEMORY_LIMIT`,
  `XATTR_QUEUE_MAX`, failed-thumbnail caches, the listings cache, undo batches
  (`MAX_UNDO_BATCHES`), the recent list, and the search result limit.
- **Process hygiene.** Every helper spawn gets a timeout with SIGTERM→SIGKILL
  escalation (`search.ts:52-72`, `plugin-install.ts:157-181`) and an armed error
  listener so a missing binary cannot ride `uncaughtException` into a crash.
- **sudo is careful.** `-n` (no prompt), password only via stdin, `--` before
  operands except the two documented `open`/`gio` cases where both operands are
  absolute paths (`elevate.ts:20-71`).
- **Plugin install is defensive.** Control-char rejection, dash-prefix and ssh
  option-injection guards, name regex, dot-prefixed staging dirs, and provenance
  re-validation on update (`plugin-install.ts:35-95`, `:308-317`).
- **Sync-browsing and the plugin dialog** both guard re-entrancy; the plugin
  confirm's poll timer is cleared on every settle path (`wiring/plugins.ts:150-188`).
- **Watchdog for native memory.** `mem-hygiene.ts` pokes the GC on a schedule
  with the reasoning documented, because native pressure alone never triggers it.

## Verdict

This is a genuinely well-engineered codebase. The hostile-input surfaces
(archive extraction, filenames, sudo, plugin install, shell helpers) are already
treated as untrusted and mostly handled correctly. No Critical issue; the two
archive findings are real gaps in an existing, mostly-correct containment
control and are the only ones worth fixing soon. Findings 3 and 4 are
performance/naming concerns, not correctness bugs. The rest is polish.

## Lean

Two changes hide the most risk for the least work: make the archive second pass
refuse link-in-link (finding 1), and make the escape sweep compare stats instead
of names so an overwrite is caught (finding 2). Together they close the entire
"malicious archive" surface. The `mount` freeze (finding 3) is a one-function
async swap.

- Real load, memory and timing numbers — all performance statements are from
  reading the code paths, not measurement.
- Windows paths (out of scope per the repo's own macOS/Linux-only design).
- The website under `docs/` and the test-suite's own coverage gaps.
